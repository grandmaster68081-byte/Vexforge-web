description: Milestone sequencing and authority boundaries for the official and experimental Unity projects.

For Vexforge, work one bounded milestone at a time on `main`. Before each milestone, fetch from `origin` and confirm a clean worktree and `HEAD == origin/main`. Commit and push each completed milestone before beginning another. Never reset, rebase, merge, cherry-pick, or force-push.

Supabase remains authoritative. Do not change live schema, RPCs, RLS, authentication, data, economy, combat settlement, or rewards. Keep the official web portal and `unity/` source intact during bootstrap work. The experimental `unity-bootstrap/` project is the cumulative destination for gradually copying the complete official game; each APK contains all slices completed so far. The user authorizes sequential continuation without per-build prompts after the baseline succeeds. A stage passes when its GitHub Actions run concludes successfully and the cumulative APK/artifact is present, intact, and its downloaded APK hash matches the report. Record BuildReport warning/error counts honestly; per the user's 2026-10-10 direction, those counts alone are non-blocking when the workflow and APK validations pass, and can be collected for review at the end. Stop on an actual failed workflow, missing/invalid APK or artifact, hash mismatch, or unresolved dependency/source issue. This does not authorize the official game workflow or Supabase changes. Follow `docs/vexforge-canonical/UNITY_BOOTSTRAP_WORKFLOW.md`.

The historical Bootstrap APK #2 was only a build-pipeline smoke test and does not count as a content milestone. Stage 5 later restored the canonical Vexforge bootstrap scene and passed with a downloaded APK whose SHA-256 matched its report. Subsequent APKs must continue building the cumulative project from original, dependency-closed slices; never add placeholder or invented game content. Report whether the prior `unity-bootstrap/Library` cache was restored by an exact or compatible key, and whether a new cache was saved.

The 5–7% canonical C# line slices applied to the early Bootstrap code stages. Stage 3 completed the full pinned runtime C# inventory; after that, stages migrate other canonical Unity content in dependency-closed batches of at most 19 files (10% of the fixed 197-file inventory). Measure, hash, and record every source slice in `unity-bootstrap/MIGRATION_MANIFEST.json`, preserve previous slices, and compile a complete APK from the accumulated state. Keep `unity/**` authoritative and do not claim full-game parity before all required content and validation are complete.

The experimental bootstrap workflow may cache only `unity-bootstrap/Library/`, after APK validation. Never cache the Unity Editor/Android toolchain, Unity Hub state, credentials, license material, or the official game's `unity/Library/`. Treat GitHub cache expiry and eviction as possible.

**Why:** the user wants the full official game represented through cumulative full APKs. The earlier 5–7% pacing covered runtime C# only; once that inventory was complete, the manifest's 10% full-content cap became the applicable measure. Intermediate APKs are not for use. The user clarified that a successful workflow with a validated APK is a passing stage even if Unity's BuildReport has a small error counter; log those counts for later collection instead of blocking the migration. The source project and live Supabase must remain intact.

**How to apply:** Before every Vexforge milestone, verify the branch/base and clean tree; keep client behavior within existing server contracts; keep both Unity workflows manual. Finish the remaining C# inventory first, then apply the fixed full-content file cap and dependency closure. Preserve prior slices and the separate package ID, and build the full accumulated APK only after the previous APK passes workflow and artifact checks. Record BuildReport counters without treating them alone as a failed stage; collect them for later review. Cache only `unity-bootstrap/Library/` after successful APK validation. Stop on actual workflow/artifact failure; never imply full parity or device verification without evidence.
